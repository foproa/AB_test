# AB_test
Data: https://www.kaggle.com/datasets/sergylog/ab-test-data/data
# A/B тест: влияние нового варианта на конверсию и выручку

## 1. Бизнес-проблема

Компания запустила новый вариант продукта/интерфейса (`variant`) и хочет понять, улучшает ли он ключевые метрики по сравнению с контролем (`control`).

**Цель теста:** проверить, влияет ли новый вариант на:
- **конверсию** — долю пользователей с выручкой > 0;
- **ARPU** — среднюю выручку на пользователя (включая нулевую).

**Бизнес-решение:** по результатам теста решить, выкатывать ли `variant` на всех пользователей.

---

## 2. Описание датасета

**Файл:** `AB_Test_Results.csv`

**Колонки:**
- `USER_ID` — идентификатор пользователя;
- `VARIANT_NAME` — группа (`control` или `variant`);
- `REVENUE` — выручка пользователя.

**Размер:** 10 000 строк, 6 324 уникальных пользователя.

**Проблемы в данных:**
- 2 660 пользователей (42.1%) имеют несколько строк;
- 1 541 пользователь (24.4%) попал в обе группы.

**Обработка:**
- пользователей из обеих групп исключили;
- для остальных выручку внутри одной группы просуммировали;
- получили одну строку на пользователя.

**Итоговая выборка:** 4 783 пользователя:
- `control` — 2 390;
- `variant` — 2 393.

**Метрики:**
- **Конверсия** = доля пользователей с `revenue > 0`;
- **ARPU** = средняя выручка на пользователя (включая нули).

### 3.1 Описательная статистика

| variant | 2393  | 42     | 1.76%      | 0.075 | 0.858  | 23.04       |

### 3.2 Проверка Sample Ratio Mismatch (SRM)

p-value = **0.9654** → SRM не обнаружен. Группы сопоставимы по размеру.

### 3.3 Гипотезы

Уровень значимости α = 0.05, тесты двусторонние.

**Конверсия:**
- H₀: p_variant = p_control
- H₁: p_variant ≠ p_control

**ARPU:**
- H₀: μ_variant = μ_control
- H₁: μ_variant ≠ μ_control

## 4. Дальнейшие шаги и проблемы

### Проблемы, с которыми столкнулись

| Проблема                          | Детали                                                                 |
|-----------------------------------|------------------------------------------------------------------------|
| Пересечение групп                 | 24.4% пользователей попали в обе группы — признак проблемы в разбиении или логировании |
| Дубли пользователей               | У 42.1% несколько строк, пришлось агрегировать выручку                  |
| Мало платящих                     | Всего 96 человек (54 в control, 42 в variant) — низкая мощность теста   |
| Выброс в control                  | Единичная покупка на 196.01 сильно тянет среднее вверх                  |
| Скошенное распределение выручки   | Поэтому использовали непараметрические тесты и бутстрап                 |

### Дальнейшие шаги

1. Выяснить, почему пользователи попадали в обе группы, и исправить разбиение/логирование.
2. Повторить тест на большей выборке и/или более длительном горизонте.
3. Заранее зафиксировать метрики и критерии остановки.
4. Исследовать выбросы и сегменты платящих пользователей.
5. Рассмотреть дополнительные метрики: ARPPU, retention, LTV.
6. **Не выкатывать `variant` по текущим результатам.**
